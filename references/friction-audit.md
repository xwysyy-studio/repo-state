# 摩擦复盘

从真实用户反馈和执行记录复原问题如何形成，确定哪个环节值得调整，并验证调整后的使用效果。任务范围由用户本轮请求决定；单个项目或工具的复盘围绕该对象取证，整体配置体检才扩展到跨项目的配置传播关系。

## 收集有出处的实例

先读取当前对象的实际实现、现状文档和操作入口。历史窗口跟随任务的发生范围。用完整问题查询用户原话，再从结果中提取文件、工具、错误名称和时间范围收窄。需要跨项目时显式指定；本轮查询及其派生总结不能作为独立历史证据重复计数。

用户反馈可以是显式不满，也可以是对用途、成本、交接、判断方法或产物的具体要求。按实际语义辨识；代码中的否定词、助手自己的认错、转发的任务书都不能独立计为用户反馈。检索结果仅部分匹配或为空时，换说法或换入口再查，不能据此判定没有该问题。

找到用户输入后，用 `context` 展开相邻对话。尤其要读清“对”“确认”“是的”所回应的提案。执行失败用 `failures` 定位，再通过 `get-tool` 读取完整命令和结果；文件变动用 `tool-history` 与 Git 对照。记录原始 session、消息或工具身份及来源位置，不另存整份会话。

资料较多且实例彼此独立时，可以让只读子代理分别核对。给任务范围、原始材料入口和待回答的问题，让它们自行判断；协调者复核原话、执行结果和当前产物。无需为一个窄问题先扫描所有配置或固定启动若干代理。

## 复原原因与处理结果

每个重要实例追到最后一个有证据的正确状态，再找到第一个偏离状态。沿中间实际发生的计划更新、委派、外部意见、规则读取和文件操作检查：是否有新用户裁定或新事实，原有信息是否在传递时被丢失，模型建议是否被当作硬要求，验证是否真正检查了消费者需要的结果。

把当时发生的故障、调用者的处理、后续是否再次出现和当前实现分开。一次查询继续返回了数据，不自动证明故障已修复；临时跳过日志、裁剪输出或更换范围，要说明它解决了什么、还遗漏什么。当前具备某项能力，也不能反推它由这次事件促成。

需要归因到配置时，只检查与因果链有关的文件及其传播关系。已有规则只能排除“完全没有规则”，不能自动证明是模型没有激活规则。先判断入口是否过时、下游是否改写了目标、权威顺序是否错误，再选择最轻的修正落点。修复现有源头优先于增加新的流程和规定。

工作量统计分清实际工具调用、外层包装、主会话与继承历史的 agent 线程。调用间隔不能直接换算模型思考或工具耗时；查询条数不能替代实际节省的工作。明确保留范围与遗漏，重复转述不增加事件频次。

## 交回与验证

按问题说明原始反馈、首次偏离、实际后果、处理结果和仍未解决的部分。结论区分已核实事实与原因推断。建议改变什么时，解释该落点为何能处理已观察到的问题；保留用户未要求改变的有效事实与功能。

仅请求复盘时先交回结论和可执行建议；已授权升级时直接在该范围内完成修改与验证。验证选择真实历史实例及一个弱语境同构任务，让新的消费者仅凭当前入口和必要原件工作，不提前透露答案或实现者结论。核对它能否取得完整依据、区分用户决定与模型建议，并正确完成实际产物。

复盘的价值由后续行为和产物判断。已有过程约束应更新到对应现状或操作入口，避免每次开工重新考古。历史检索对明确说出口的摩擦更敏感，沉默返工和记录缺失仍可能遗漏；结论强度以实际证据覆盖为限。
